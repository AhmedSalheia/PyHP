# 1.0.0-rc1 review: findings and fixes

A review of `v1.0.0-rc1` (2026-11-13) reported five findings. Each was reproduced before anything was changed; none could be dismissed, so all five are fixed, plus one more of the same kind found while checking finding 2. The tests are `tests/python/test_hardening.py` and `tests/php/HardeningTest.php`; each fails without its fix.

| # | Finding | Verdict | Fix |
|---|---|---|---|
| 1 | An unauthenticated local connection can crash the worker during start-up with a token holding an escaped unpaired surrogate (`"\ud800"`): `offered.encode()` raised outside the guarded block. | **Real**, reproduced. Narrower than it sounds: it needs a local process racing PHP to the port in the milliseconds before PHP connects, and the result is a failed start (`WorkerStartException`), never a bypass of the token check. | The token is encoded inside the check; a token that can't be encoded is refused like a wrong one, and the worker keeps waiting for PHP. |
| 2 | `pyhp info` runs Python files from the current directory: its `python -c` probe imported `json` with the working directory first on `sys.path`. | **Real**, reproduced with a marker file. Matters when diagnosing a project you don't trust. | The probe's first line removes the working directory from `sys.path` before importing anything. `-I` was not used: it also hides user site-packages, which the worker sees, so `info` would report packages as missing. |
| 2b | *Found while checking 2:* without uv, `pyhp setup` runs `python -m venv` and `python -m pip` from the project folder, and `-m` also puts the working directory first, so a `venv/` or `pip.py` in the project would run. | **Real**, reproduced. | Both run with `-P` (Python 3.11+, which PyHP requires), which keeps the working directory off `sys.path`. |
| 3 | Output can end a healthy session: with `max_message_bytes=1024`, `print('A' * 1100)` made the worker send a `too_large` error that was itself above the limit, and PHP closed the session. Printing an unpaired surrogate crashed the worker while encoding the response. | **Real**, both reproduced. Live output had the same size problem: it was sent in pieces of up to 16,000 characters regardless of the limit. | Responses are fitted to the limit: the output keeps its end behind a note saying how much was cut, then an error loses its traceback and its message is cut. Only a value that is itself too large fails, and that error is fitted the same way. Live output is split into frames that fit. Every frame is encoded with invalid Unicode replaced by `?`. |
| 4 | Inline source accumulates for the lifetime of a worker: every `exec()`/`eval()` adds an entry to `linecache.cache`. | **Real**, reproduced (100 evaluations, 100 entries). Small per call, but unbounded in a long-running shared session. | Only the 1,000 most recent snippets keep their source for tracebacks (`MAX_SNIPPETS`). |
| 5 | Diagnostic output exposes complete requirement URLs, including credentials. | **Real.** | `pyhp info` (text and `--json`) and `pyhp setup` hide the user part of URLs (`https://***@host/...`) in everything they print. Commands still get the real URL. Query-string tokens are not redacted; the docs recommend keeping credentials out of `composer.json` (environment variables in requirements files, `.netrc`, keyrings). |

None of the fixes changes the public API or the wire protocol (still 4).
